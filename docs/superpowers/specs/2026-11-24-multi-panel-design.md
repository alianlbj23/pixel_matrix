# PixelBoard Studio：多面板排列設計

日期：2026-11-24　狀態：草稿
前提文件：`2026-11-24-gif-studio-design.md`（下稱「主設計」）。本文件只寫新增和改變的部分。

## 1. 這是什麼、為什麼要做

主設計只支援 1 塊面板，或 2 塊面板左右排成一排。

使用者的需求有兩個：
- 面板可能**不只 2 塊**。
- 面板的**擺放方式**也不一定是一排，可能是上下疊、2×2，或是有幾塊倒著裝。

非本科系的使用者看不懂 HUB75 排線的串接順序。所以設定的方式要做得像 **Windows 的多螢幕設定**：
1. 按「辨識」，每塊實物面板顯示自己的編號。
2. 在程式裡拖曳方塊，排成跟實物一樣，方塊會自動吸附對齊。

另外，燒錄期間所有設定都要鎖住，不能修改。

**成功的標準：**
- 拿到 3 塊面板、擺成 L 形的使用者，不用看說明就能在 2 分鐘內排好。
- 燒錄後，GIF 在每一塊面板上的位置和方向都跟預覽一致。

## 2. 使用者確認過的需求

以下是使用者原話或使用者同意過的內容：

1. **辨識面板**：像 Windows 偵測多螢幕時，每個螢幕顯示 1、2、3。每塊實物面板顯示自己的串接編號和「上方」箭頭。
2. **面板編輯器**：
   - 可以設定面板數量。
   - 每塊面板是一個可以拖曳的方塊，標著串接編號。
   - 拖到另一塊旁邊（上、下、左、右）時**自動吸附**。
   - 點一下可以旋轉，對應倒著裝的面板。
3. **燒錄時鎖定設定**：燒錄期間，GIF、音樂、排列、位置、亮度等設定全部變灰，不能動。燒錄完成，或使用者按「**停止燒錄**」之後，才能繼續編輯。
4. **試聽可以停止**：已經完成，commit `6a31fa8`。
5. 使用者同意「照 Claude 的建議做」，所以第 4 節的決定都由 Claude 做，使用者可以推翻。

## 3. 目標 / 非目標 / 反目標

### 目標
- 支援 1 到 **8** 塊串接的 64x32 面板，擺法任意，每塊可以旋轉 0、90、180 或 270 度。
- 「辨識面板」是即時的，**不需要燒錄**，幾秒內就能在實物上看到編號。
- 預覽顯示實際排列的樣子，面板之間的空隙不會顯示內容，也不會被燒錄。
- GIF 有兩種放法：
  - **整張**：鋪滿所有面板圍成的外框。
  - **每塊一份**：面板剛好排成規則的 R 列 × C 欄時，把 GIF 的可見內容切成 R×C 份，每塊放一份。這是現在「左右眼」做法的推廣。
- 排列設定在燒錄時一起寫進板子；面板數也由這份設定決定。

### 非目標（這一版不做）
- 每塊面板放不同的 GIF（使用者同意之後再做）。
- 自動偵測面板數量。HUB75 面板只能接收資料，不會回報，所以數量要由使用者輸入。
- 同一條排線上混用不同尺寸的面板。

### 反目標
- 使用者需要了解「排線順序」或「蛇形串接」這類名詞才能設定成功。
- 預覽跟實物的位置或方向不一致。
- 在寫入韌體的過程中可以按停止，導致板子無法開機。
- 燒錄中還能修改設定，造成寫進去的內容跟畫面上看到的不一樣。

## 4. Claude 的技術決定（builder 可以挑戰）

### 4.1 排列換算全部在電腦上做
- 程式把 GIF 先畫在「排列外框」上，外框是所有面板的聯集範圍，單位是 LED 像素。
- 接著依照每塊面板的位置和旋轉，把對應的像素搬到「排線順序」的緩衝區：寬是 64 x N，高是 32，第 i 塊面板佔 x = 64i 到 64i+63。
- 寫進板子的就是這個排線順序的資料。
- **韌體只要知道 N，依序把資料送出去，不需要懂排列。**
- 原本的「左右對調」選項取消，改用編輯器拖曳來處理。韌體裡的 `panel_x`/swap 保留相容，但新資料一律寫 0。
- **一致性的保證**：預覽畫的是排列外框上的畫面。換算是單射（每個面板像素只對應外框上的一個點），所以測試要驗證：「把燒錄資料反向換算回外框」等於「預覽中位於面板內的像素」。

### 4.2 面板座標和吸附
- 每塊面板記錄四個值：`x`、`y`（左上角，LED 像素，整數）、`rotation`（0、90、180、270）、`index`（串接順序，0 起算）。
- 旋轉 90 或 270 度時，面板佔的範圍是 32 寬 × 64 高。
- **吸附規則**：
  - 拖曳放開時，如果這塊的某個邊離其他面板的某個邊在 **8 個 LED 像素**以內，就對齊過去。
  - 左邊可以貼齊別塊的右邊，上邊可以貼齊別塊的下邊，依此類推，並且盡量讓兩塊的邊緣也對齊。
- **重疊**：面板不能重疊。放開時如果重疊，就退回拖曳前的位置。
- 面板數改變時：
  - 增加：新的面板接在最右邊。
  - 減少：移除編號最大的那塊。
- **預設**提供「一排橫放」「直的疊起來」「2×2」「蛇形 2×2」幾種一鍵排列，只是方便用，使用者仍然可以拖曳調整。

### 4.3 辨識面板（USB 指令，不燒錄）
- 程式透過 COM port 送一行文字指令給韌體，例如 `PXB IDENTIFY <N>\n`。
- 韌體收到後：
  1. 用 N 塊面板重新初始化 HUB75。
  2. 在第 i 塊面板上，用大字畫出編號 i+1，加上一個指向面板「上方」的箭頭。
  3. 5 秒後，回到原本的 GIF 和面板設定。
- 韌體要用一個小 task 讀取 USB Serial/JTAG 的輸入。指令格式要嚴格驗證：N 只能是 1 到 8，其他格式一律忽略並記 log。
- **未驗證的風險**：開啟 COM port 時，可能會讓 ESP32-S3 的 USB Serial/JTAG 重設晶片（之前觀察到開啟序列埠後板子有重開）。
  - 實作計畫的**第一步**要先用實機驗證：能否在不重設的情況下開啟 port 並送出指令，例如控制 DTR/RTS。
  - 如果一定會重設：程式就等韌體開機後印出 `PXB READY`，再送指令。辨識會慢大約 5 秒，但仍然不需要燒錄。
- 字型要補上數字 0–9 和箭頭，以 3 倍大顯示。
- **實測結果（2026-11-24，WSL/Linux）**：開啟 port 時把 DTR 設為 True（RTS 設 True 或 False 都可以），板子**不會重開**；DTR 為 False 時每次都會重開。Windows 的行為要在實作時用 exe 再確認一次。
- **韌體回覆**：收到合法指令後，韌體回一行 `PXB OK IDENTIFY <N>`；格式錯誤時回 `PXB ERR <原因>`。程式等回覆最多 1.5 秒。
- **板子的韌體還不支援辨識時**（全新的板子，或舊版韌體）：程式等不到回覆，就顯示「這塊板子還沒有新版韌體，請先按『安裝/更新韌體』」。
  - 介面另外提供一個「**安裝/更新韌體**」按鈕：只寫入 bootloader、分割表和韌體，不寫 GIF 和音樂。
  - 這走的是原本的 `plan_flash`，鎖定和停止規則也一樣（第 4.6 節）。
  - 所以第一次使用的流程是：安裝韌體 → 辨識 → 排列 → 加入 GIF → 燒錄。

### 4.4 資料格式和容量
- PXG1 的 `chain` 範圍從 1–2 放寬到 **1–8**。
- 格式版本升到 2，旗標 bit0 swap 保留但不再使用。韌體同時接受版本 1 和 2。
- 版本 2 在畫面資料之前多存一張**排列表**：每塊面板 8 bytes，內容是 x(i16)、y(i16)、rotation(u16，以度為單位)和保留欄位，再加上版面模式（整張或每塊一份）。
  - 韌體不使用這張表，只檢查長度和 CRC。
  - 存這張表是為了以後能從板子讀回排列（例如換一台電腦），或是做「每塊放不同 GIF」時不用再改格式。
  - 這一版**不做**讀回功能；電腦上的 `layout.json` 才是主要的來源。
- **容量**：每塊面板每格 6KB，8 塊就是 48KB。原本 1MB 的 GIF 區只放得下 21 格，所以分割表改成：

  | 名稱 | 大小 | 位置 | 說明 |
  |---|---|---|---|
  | factory | 2M | 0x10000 | 不變 |
  | gif | **3M** | 0x210000 | 8 塊面板約可放 64 格 |
  | audio | **10M** | 0x510000 | 從 12M 縮成 10M |

  - 因為 audio 的位置改了，舊板子在首次安裝或更新韌體後，**音樂需要重新加入**。主設計已經有這個提示。
  - 音樂容量的顯示從 12MB 改成 10MB。
- **格數上限**改成依面板數計算：`min(64, gif 區大小 / 每格大小)`。超過時，載入 GIF 就要用白話提示，例如「8 塊面板時最多 62 格」。

### 4.5 韌體和硬體限制
- 面板越多，HUB75 的更新率越低，函式庫會自動降低色彩深度。8 塊時要實測，確認不會明顯閃爍；如果會，就在程式裡把上限降到實測可接受的數量，並說明原因。
- DMA 緩衝區每塊約 16KB，8 塊約 128KB，在目前約 370KB 的可用記憶體內。要實測確認，含音樂播放。
- 介面在面板數 ≥ 3 時要提示：「多塊面板需要夠大的 5V 電源，不能只靠 USB 供電」。

### 4.6 燒錄中鎖定和停止燒錄
- 燒錄開始後，除了「停止燒錄」按鈕，所有設定控制項都停用並顯示灰色，包括檔案拖放。
- **可以停止的時機**：
  - 寫入 **gif 區或 audio 區**時，可以停止。程式在每寫完一小段（例如 64KB）後檢查停止要求，所以按下後約 1 秒內就會停。
  - 寫入 bootloader、分割表或韌體時，按鈕變灰，並顯示「正在寫入韌體，請稍候」。
- **停止之後**：
  1. 重設板子。這時被中斷的區塊 CRC 會不對，所以畫面顯示 NO GIF，或者沒有音樂。
  2. 介面顯示「已停止燒錄：板子上的 GIF/音樂可能不完整，請重新燒錄」。
  3. 所有設定恢復可以編輯。

### 4.6b 「每塊一份」的判斷
- 不要求面板緊貼。只要所有面板的旋轉方向都一樣，而且依位置可以分成整齊的 R 列 × C 欄，就可以使用「每塊一份」：
  - 同一列的面板 y 相同。
  - 同一欄的面板 x 相同。
  - 面板之間可以有空隙。
- 典型的例子是兩塊分開安裝的眼睛。
- 每塊面板放 GIF 可見內容的第 (r, c) 份。空隙本來就不畫，所以不會遺失內容。
- 不符合條件時，這個選項變灰，並說明「這種排法只能用整張」。

### 4.7 排列設定的保存
- 排列（面板數、位置、旋轉）存在電腦上的 `%LOCALAPPDATA%\PixelBoard-Studio\layout.json`，下次開啟時自動載入。
- 讀取失敗時，用預設「1 塊」，並記錄 log。

### 4.8 開發者流程（menu.sh）
- `tools/pack_gif.py` 新增 `--layout <layout.json>` 參數，格式跟 Studio 存的 `layout.json` 相同，兩者共用同一份 Python 程式碼。
- 沒有給 `--layout` 時，沿用原本的 `--chain N`，視為「一排橫放」。
- `menu.sh` 的「Convert GIF」：如果 `assets/layout.json` 存在就使用它，沒有就用一排。不另外做互動式的排列選單；要排列的話，用 Studio 編好再存檔。

## 5. 留給 builder 決定

- 辨識畫面中編號和箭頭的確切畫法。
- 「每塊一份」在不規則排列下的提示文字（例如顯示「這種排法只能用整張」並停用選項）。
- 測試的切法：
  - 換算、吸附、重疊判斷、格數上限都是純 Python，要有正常和錯誤情況的測試。
  - 韌體的指令解析要有 host 測試。
  - 8 塊面板的實機測試，如果手邊沒有 8 塊，就用現有的 2 塊加上模擬 N 塊的資料，並把「未實測 8 塊」記錄下來。
